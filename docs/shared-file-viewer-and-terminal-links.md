# Shared file viewer and terminal links

Shared files have **View** and **Download** actions in the conversation and terminal downloads list. Text opens inside a themed dialog. Markdown (`.md`, `.markdown`, `.mdown`, `.mkd`) and HTML (`.html`, `.htm`) have **Rendered** and **Text** views. Closing the viewer returns to the file list. HTML also has **Open in new tab** for viewing at full browser size.

The collection is shared across an agent's sessions. Deleting a saved conversation retains the agent's files and images;
see [agent artifacts](agent-artifacts.md) for retention, permissions and access from other agents through `dam-tools`.

The Markdown viewer reuses the existing [Markdig](https://github.com/xoofx/markdig) dependency. It uses a file-specific pipeline for headings, tables, task lists, emphasis, autolinks and fenced code; raw HTML, generic HTML attributes and executable media extensions are disabled. Text view uses Blazor text escaping or the browser's plain-text viewer. Explicit web links open a separate tab with opener/referrer isolation. Unavailable relative Markdown links are neutralized rather than navigating the Manager. Existing fragment links remain local to the rendered document.

There is no preview size cap. The existing publication limit of 1 GiB still applies. The metadata endpoint reads at most 512 KiB to recognize text and returns small text inline; larger text streams directly to a browser frame with range support, without buffering the complete file in the Manager or serializing it into JSON. UTF-8 and BOM-marked UTF-16 are supported. Invalid encodings and binary control characters in the sample retain the original Download action. Large Markdown starts as streamed text; choosing Rendered downloads and renders it in the browser on demand. Very large content can still consume browser memory. HTML always streams directly, including large pages containing base64 images. Opening a preview never changes the shared original. Each preview has its own loading placeholder and retry path.

## HTML websites and assets

HTML uses the browser's renderer in an iframe with an opaque origin. Inline scripts, event handlers, CSS, embedded images, public HTTP(S) resources, fonts and media work. Relative dependencies such as `assets/chart.png`, `site.css`, `site.js` and `config.json` resolve against other files/images published by the same agent. Assets must be shared separately; private Runner paths and unpublished neighboring files are not exposed. Published filenames currently contain only the basename, so directory segments are ignored during lookup. The page's original publishing session takes precedence; ambiguous names elsewhere in the collection return not found. Resources remain within the viewer's current read permissions, including the narrower permissions of a session-only share.

The iframe and the response's CSP both apply sandbox restrictions, including in a new tab. They allow page scripts while excluding `allow-same-origin`: scripts cannot read the Portal DOM, cookies, local storage, authenticated API responses or remove their own sandbox. Forms, nested frames and top-level navigation are blocked. Popups inherit the sandbox. Pages retain their original bytes and layout; no HTML sanitizer or document rewriting is needed. See the browser documentation for [iframe sandbox behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox) and the [CSP sandbox directive](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox).

Sandboxed resource requests do not carry Portal cookies. The authenticated metadata endpoint therefore issues a protected, two-hour preview URL scoped to the root file and its readable published dependencies. Each GET revalidates the originating browser sign-in, security stamp, local/public boundary and current conversation read permission. Logout, account disabling, removed shares and deletion revoke subsequent reads. Resource responses allow CORS for these scoped GET URLs so fonts, JavaScript modules and JSON work from the opaque frame; credentialed CORS is never enabled. Preview URLs must be treated as temporary read credentials. No-referrer headers prevent them being sent to external assets. Responses use private/no-store and nosniff headers, and downloads retain their attachment behavior.

Terminal links use [xterm's link handling](https://xtermjs.org/docs/guides/link-handling/) for both ordinary URLs and named OSC 8 links. Each terminal installs its own web-links addon and OSC 8 handler. Only absolute HTTP(S) URLs are opened. A short phone tap asks xterm's existing providers to resolve the touched cell and opens the URL on the viewing device. Link mouse/touch gestures are consumed before terminal mouse reporting can forward them to tmux or the harness. Swipes, long presses, normal terminal clicks and Shift selection retain their respective behavior. Handlers and addon subscriptions are disposed with the terminal. No browser setting or command is changed on the Runner.

The browser's tmux attachment declares `RGB,hyperlinks` with tmux's per-client `-T` option. Without the hyperlink capability, tmux removes the embedded target of a named link before xterm receives it. This applies to writable and read-only viewers, including viewers joining an existing terminal. Reconnecting the browser terminal applies it to already-running agents; no harness restart, Runner setup or global tmux configuration change is needed.

## Verification

`SessionFilePreviewTests` covers encodings, streaming boundaries, binary data and Markdown rendering safety. `SessionFileApiTests` covers conversation permissions, a 10 MiB HTML page, scoped assets, revocation, range reads, plain-text streaming and response headers. `DeveAgentManager.Tests/Browser/file-viewer.mjs` checks both modes, loading/retry, fallback downloads and phone/light/dark layouts. `html-viewer.mjs` uses real HTTP with a 10 MiB page, embedded/external/relative images, CSS, scripts, JSON, source/new-tab views, parent/cookie/API isolation and large text/Markdown. Both run in the existing isolated CI browser wrapper. `TerminalLinkTransportTests` checks actual tmux PTY output using the production attachment script, with a negative control that reproduces lost link targets. `terminal-links.mjs` checks direct and real-tmux output for URL and named-link clicks/taps, fragments, blocked protocols, swipe gestures and unchanged ordinary mouse reporting. Browser tests use an isolated development Manager with test-only credentials; the HTML test additionally requires its disposable data directory as `DAM_TEST_DATA_DIR`.
